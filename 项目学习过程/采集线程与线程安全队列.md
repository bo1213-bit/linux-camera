# Linux 相机应用开发（二）· 采集线程与线程安全队列

> 接上一篇《linux相机应用开发.md》：上一篇把「裸采集」跑通了，能抓 10 帧 MJPEG 存成 `.jpg`。
> 本篇讲路线图的第 ② 步：把采集逻辑封装成**采集线程**，用**互斥锁 + 条件变量**做一个**线程安全队列**，为第 ④ 步 RTP 传输铺路。
> 本篇解决 `learning_gaps.md` 里的第 7、8、9、10 条盲区。

---

## 1. 为什么：从「写文件」到「喂队列」

回顾上一篇的裸采集程序，它的主循环长这样（`v4l2app.cpp` 第 190~226 行）：

```cpp
for (int n = 0; n < 10; n++) {          // 抓 10 帧就停
    ioctl(fd_, VIDIOC_DQBUF, &frame);   // 出队取帧
    // ... open() 写文件 ...
    write(f, data, frame.bytesused);    // 存成 frame_n.jpg我看了代码和文档。先给你一个明确的结论，再纠正一个顺序上的小偏差。
    close(f);
    ioctl(fd_, VIDIOC_QBUF, &frame);    // 还回
}
return 1;                               // 抓完直接返回，程序结束
```

这个结构**只适合"抓几帧存起来看看"**，有三个致命问题：

1. **抓完就停**：`n < 10`，程序跑一下就退出了，不可能"实时"。
2. **采集和消费串在一起**：取到一帧 → 立刻写文件 → 才取下一帧。写文件（将来是发网络）慢的话，摄像头等不到空闲缓冲，采集就被拖慢。
3. **没有并发**：将来"一边采集一边发网络"根本无从谈起——现在只有一条路，所有事都得排队走这一条路。

所以下一步要把"取帧"和"用帧"**拆开**，让它们能**同时**跑。这正是 `learning_gaps.md` 第 7 条说的多线程的两个核心机制：

| 机制 | 说明 | 反例（单线程会怎样） |
|---|---|---|
| **① 避免阻塞互拖** | 一个阻塞调用（等帧 / 等网络）不该让别的任务停摆 | 等摄像头出帧时，控制指令收不到；发网络卡住时，采集也停 |
| **② 流水线并行** | 采第 N+1 帧的同时，正在编/发第 N 帧 | 单线程里总耗时 = 采集+编码+发送 三步**之和**；并行后 ≈ 最慢的那一步 |

---

## 2. 生产者-消费者模型

拆开后的结构是经典的生产者-消费者：

```
┌─────────────┐         ┌──────────────┐         ┌─────────────┐
│  采集线程     │   push  │  线程安全队列  │   pop   │  发送线程     │
│ (生产者)      │ ──────► │  (中间缓冲)   │ ──────► │ (消费者)      │
│ DQBUF取帧     │         │  一堆排队的帧  │         │ 拆包发 UDP   │
└─────────────┘         └──────────────┘         └─────────────┘
```

- **生产者（采集线程）**：不停地 DQBUF 取帧，把帧**塞进队列**，然后立刻取下一帧。
- **消费者（发送线程）**：从队列**取出一帧**，慢慢处理（拆包、发网络），处理完再取下一帧。
- **队列**：夹在中间，吸收两边的速度差——采集快、发送慢，队列里就攒几帧缓冲。

> 这个队列就是 `learning_gaps.md` 第 8 条说的「环形缓冲区」思路的落地：它**不是"存很多东西"，而是"固定大小的缓冲，循环复用 + 天然 FIFO"**。谁先放进去谁先出来，正适合"先采集的先发送"。

## 3. 一帧在队列里怎么表示（本篇最大的坑）

这是从「裸采集」进化到「线程间传帧」时**最容易踩的坑**，先说清楚。

### 3.1 为什么不能直接传 mmap 指针

裸采集程序里，帧数据在 `buffers_[frame.index]`（mmap 映射出来的指针），DQBUF 后直接用、用完 QBUF 还回去——**这个"用"是同步的，用完立刻还，没问题**。

一旦异步化，问题就来了：你只有 **4 块 mmap 缓冲**，它们是**循环复用**的。如果采集线程 DQBUF 出第 0 块，把指针丢进队列就不管了、继续去 DQBUF 下一块——那么：

- 消费者还没来得及读这块数据，
- 采集线程已经把这块 **QBUF 还回去**了，
- 内核又往这块**写入新一帧**……

消费者读到的就是**脏数据**（一半旧帧一半新帧，花屏）。

**结论：mmap 缓冲是内核的，DQBUF 出来的指针只能在"下次 QBUF 之前"短暂有效。不能直接跨线程传。**

### 3.2 正确做法：DQBUF 后拷贝一份，立刻 QBUF 还回

```cpp
// 采集线程里，DQBUF 取到一帧后：
unsigned char *raw = (unsigned char *)buffers_[frame.index];
size_t n = frame.bytesused;

// ① 拷贝一份到新内存（帧数据从此归"我"管，与内核那 4 块无关）
unsigned char *copy = new unsigned char[n];
memcpy(copy, raw, n);

// ② 立刻 QBUF 还回，内核马上能继续用这块
ioctl(fd_, VIDIOC_QBUF, &frame);

// ③ 把"拷贝出来的帧"塞进队列
Frame f{copy, n};
queue.push(f);
```

### 3.3 为什么拷贝是值得的

- **解耦**：生产者 new 出一份独立内存，消费者用完后 `delete[]`，两边的生命周期互不干扰。
- **简单**：不用搞引用计数、信号量那套复杂同步。
- **代价小**：MJPEG 一帧才 15~40KB，`memcpy` 一份不到 1 毫秒；而采集一帧（30fps）有 33 毫秒，这点拷贝微不足道。

> 注意「零拷贝」这个词不要用错：`mmap` 的零拷贝指的是**内核缓冲 → 用户空间**不需要 `read()` 那次拷贝。现在这次 `memcpy` 是**用户空间内部**的一次拷贝，目的是"把帧从内核缓冲里抢救出来、独立拥有它"，性质完全不同，该拷就拷。

### 3.4 帧的结构体

```cpp
// 队列里流转的"一帧"
struct Frame {
    unsigned char *data;  // 拷贝出来的帧数据（生产者 new，消费者 delete[]）
    size_t size;          // 实际字节数 = frame.bytesused（MJPEG 每帧不一样！）
};
```

**内存所有权约定**：生产者 `new` → 塞队列 → 消费者 `delete[]`。谁都不许忘记，否则泄漏。

## 4. 线程安全队列的设计（mutex + 条件变量）

队列本身用 C++11 标准库三件套：`std::queue` + `std::mutex` + `std::condition_variable`。**不用无锁队列**——这是 `learning_gaps.md` 第 10 条的结论：无锁（CAS 原子操作）对这个项目是过度优化，`mutex + 条件变量` 简单够用、不容易错。

### 4.1 最小可用的队列

```cpp
#include <queue>
#include <mutex>
#include <condition_variable>

class FrameQueue {
public:
    // 生产者：塞一帧进去
    void push(Frame f) {
        {
            std::lock_guard<std::mutex> lk(mtx_);   // 锁住，操作完自动解锁
            q_.push(f);
        }
        cond_.notify_one();   // 通知：队列里现在有东西了，睡着的消费者该醒了
    }

    // 消费者：取一帧出来；队列空就阻塞等，不忙等
    Frame pop() {
        std::unique_lock<std::mutex> lk(mtx_);
        cond_.wait(lk, [this] { return !q_.empty(); });  // 空就睡，被唤醒再检查
        Frame f = q_.front();
        q_.pop();
        return f;
    }

private:
    std::queue<Frame> q_;
    std::mutex mtx_;
    std::condition_variable cond_;
};
```

### 4.2 条件变量的两个作用（呼应 learning_gaps 第 9 条）

- **作用一：通知唤醒** —— `notify_one()` 把睡着的消费者叫醒"有帧了"。
- **作用二：空时休眠，避免忙等** —— 消费者 `wait()` 时队列空，就**释放锁、睡过去**，CPU 不空转。如果不用条件变量、光用锁，消费者只能 `while(空){解锁; 检查; 加锁;}` 死循环，白白烧 CPU——这就是"忙等"。

> 注意 `wait` 要配 `unique_lock` 而不是 `lock_guard`，因为 `wait` 需要"暂时解锁让生产者能进来、被唤醒后再重新加锁"。`lock_guard` 做不到中途解锁。

### 4.3 队列要不要有上限？（有界队列 + 丢旧帧）

上一版队列是**无界的**：采集 30fps、发送慢的话，队列无限涨，内存爆炸。

视频场景的正确做法是**有界队列 + 丢最旧帧**：满了就把队头（最旧）丢掉，永远保证队列里是最新的几帧。这呼应 `learning_gaps.md` 第 4 条的精神——**实时视频宁可丢帧，也不该让延迟越来越大**。

```cpp
class FrameQueue {
public:
    explicit FrameQueue(size_t maxSize = 4) : maxSize_(maxSize) {}

    void push(Frame f) {
        {
            std::lock_guard<std::mutex> lk(mtx_);
            if (q_.size() >= maxSize_) {        // 满了
                delete[] q_.front().data;       // 丢最旧一帧（释放它的内存！）
                q_.pop();
            }
            q_.push(f);
        }
        cond_.notify_one();
    }

    Frame pop() {
        std::unique_lock<std::mutex> lk(mtx_);
        cond_.wait(lk, [this] { return !q_.empty(); });
        Frame f = q_.front();
        q_.pop();
        return f;
    }

private:
    std::queue<Frame> q_;
    size_t maxSize_;
    std::mutex mtx_;
    std::condition_variable cond_;
};
```

> ⚠️ 丢帧时记得 `delete[] q_.front().data` 再 `pop`，否则那一帧的 `new` 出来的内存就泄漏了。

## 5. 采集线程的改造

把上一篇 `v4l2_APP` 里"抓 10 帧写文件"的 for 循环，改成一个**线程函数**，主循环是"取帧 → 拷贝 → 塞队列"，永不停止（直到收到退出信号）。

### 5.1 采集线程主循环

```cpp
// 采集线程：作为类的成员函数运行，或者一个独立函数，通过参数拿到 fd 和队列
void captureLoop(FrameQueue &queue) {
    struct v4l2_buffer frame = {0};
    frame.type   = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    frame.memory = V4L2_MEMORY_MMAP;

    while (running_) {                          // running_ 是退出标志（见 5.3）
        // ① 等新帧（select 带超时，呼应上一篇第 8 节，避免 DQBUF 一直卡住）
        fd_set fds;
        struct timeval tv = {2, 0};             // 2 秒超时
        FD_ZERO(&fds);
        FD_SET(fd_, &fds);
        int r = select(fd_ + 1, &fds, NULL, NULL, &tv);
        if (r <= 0) continue;                   // 超时或出错：回到循环开头，顺便检查 running_

        // ② 取帧
        if (ioctl(fd_, VIDIOC_DQBUF, &frame) < 0) continue;

        // ③ 拷贝一份
        unsigned char *copy = new unsigned char[frame.bytesused];
        memcpy(copy, buffers_[frame.index], frame.bytesused);

        // ④ 立刻还回（别等消费端，马上让内核继续用这块）
        ioctl(fd_, VIDIOC_QBUF, &frame);

        // ⑤ 塞队列（满了会自动丢最旧帧）
        queue.push(Frame{copy, frame.bytesused});
    }
}
```

### 5.2 关键点对比：裸采集 vs 采集线程

| | 裸采集（上一篇） | 采集线程（本篇） |
|---|---|---|
| 循环条件 | `for (n < 10)` 抓 10 帧 | `while (running_)` 一直跑 |
| 取帧方式 | 直接 DQBUF（阻塞） | `select` 带超时再 DQBUF |
| 用帧方式 | 写文件 | `memcpy` 拷贝 + 塞队列 |
| QBUF 时机 | 写完文件才还 | **拷贝完立刻还**（不等消费） |
| 结束 | `return 1` | 收到退出信号，`running_ = false` |

### 5.3 优雅退出：running_ 标志

多线程程序不能靠"直接 return"结束——别的线程可能还在跑。要用一个**共享标志**让循环自己退：

```cpp
std::atomic<bool> running_{true};   // 原子类型，多线程读写都安全

// 主线程想退出时：
running_ = false;                   // 采集线程下一轮 while 检查到就退
```

> 消费者那边的 `pop()` 如果队列空会一直 `wait` 睡死，退出时要保证它也能被唤醒——最简单是退出前再 `notify_one()` 一下，或者给 `pop` 也加上 `running_` 判断。这个细节等第 ⑤ 步做完整管道时再细化，现在先知道"要有退出机制"这个概念即可。

## 6. 串起来：main 里的结构

```cpp
int main() {
    v4l2_APP cam;
    if (!cam.openDevice("/dev/video0")) { /* ... */ }
    cam.initCapture(640, 480);            // QUERYCAP + S_FMT + REQBUFS + mmap + QBUF + STREAMON

    FrameQueue queue(4);                  // 有界队列，最多 4 帧

    // 启动采集线程
    std::thread producer(&v4l2_APP::captureLoop, &cam, std::ref(queue));

    // 主线程暂时当消费者（下一步换成"发送线程"，把帧发出去）
    while (true) {
        Frame f = queue.pop();
        // 这里暂时验证一下：存成 jpg，确认队列里拿到的是完整帧
        // 下一步就把这里改成"拆包发 UDP"
        delete[] f.data;                  // 用完记得释放！
    }

    producer.join();                      // 等采集线程结束
    return 0;
}
```

> 现在消费者还用"存文件"来验证，是为了让你确认**队列里流通的帧是完整的**。验证通过后，下一步只要把 `pop()` 出来之后的处理换成"拆包发 UDP"，管道就通了。

## 7. 编译与运行

多线程要加两个东西：C++11 标准 + pthread 库。

```bash
g++ -std=c++11 -pthread v4l2app.cpp -o v4l2app
sudo ./v4l2app
```

> ⚠️ 忘记 `-pthread` 会报 `undefined reference to pthread_create`。`<thread>` `<mutex>` `<condition_variable>` 这些头文件本身不需要链接库，但 `std::thread` 底层依赖 pthread，所以链接时必须加。

## 8. 常见坑汇总

| 坑 | 后果 | 解决 |
|---|---|---|
| 跨线程直接传 mmap 指针 | 缓冲被复用，读到脏帧/花屏 | **DQBUF 后 memcpy 一份**（第 3 节） |
| 忘记 `-pthread` | 链接报错 | 编译命令加 `-pthread` |
| 消费者忘了 `delete[] f.data` | 每帧泄漏 15~40KB，跑久了内存耗尽 | 记住"生产者 new、消费者 delete" |
| 丢帧时只 `pop` 不 `delete[]` | 同上，丢掉的帧内存泄漏 | 丢之前先释放 `front().data` |
| 用 `lock_guard` 配 `wait` | 编译报错 | 条件变量必须用 `unique_lock` |
| 无界队列 | 采集快发送慢时内存暴涨 | 用有界队列 + 丢旧帧 |
| 空队列死循环 `while(空)` 忙等 | CPU 100% 空转 | 用条件变量 `wait` 让消费者睡 |
