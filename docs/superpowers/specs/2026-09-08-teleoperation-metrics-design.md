# 机械臂遥操作系统 — 技术指标规格

- 日期：2026-09-08
- 项目：基于 Linux 双板协同的机器人远程遥控与遥测系统
- 阶段：架构设计（技术指标规格）

---

## 0. 目的与背景

本项目当前只实现了「视频单向链路」：UVC MJPEG 摄像头 → V4L2 采集 → 自定义分片 → UDP 发送（接收端能收齐存成 jpg 验证）。控制指令通道、遥测上报、接收端解码显示均未实现。

要让它从一个「能跑通」的 demo 变成一个「有技术指标可对标」的工程，必须先把应用场景定死，再从场景倒推指标。**指标的技术意义来自「立靶 → 实测 → 校准」的闭环**，而不是数字本身好看。

本文档的产出：一套 20 条技术指标，每条都有「为什么是这个数」的推导，并标注【当前可测】还是【需补齐模块】。

### 0.1 场景决策（已确认）

| 维度 | 决定 |
|---|---|
| 应用场景 | 机械臂遥操作，**精细操作类**（抓取/装配/微调对位，手眼需精准协调） |
| 网络 | 阶段 1 有线网口直连 → 阶段 2 WiFi |
| 画质 | **640×480 @ 30fps** |
| 视频编码 | UVC 摄像头内部硬件 MJPEG 直传（机器人端零软件编码） |

> 设计取舍说明：MJPEG 比 H.264 大 3~10 倍带宽，但 UVC 摄像头在硬件内完成编码，机器人端 CPU 只做「采集拷贝 + 拆片 + sendto」。这是「拿带宽换省 CPU」的取舍——后续 M3（码率）、M1（CPU）指标正是用来验证这个取舍值不值的。

## 2. 指标明细

### 2.1 功能层（F）

| # | 指标 | 目标值 | 备注 |
|---|---|---|---|
| F1 | 视频分辨率 / 帧率 | 640×480 @ 30fps | 由摄像头硬件能力决定上限；当前代码已是此档 |
| F2 | 视频编码 | MJPEG（UVC 硬件产出） | 直传，不做软件编码 |
| F3 | 控制指令集 | 启动/停止流、设分辨率帧率、运动控制（前后左右）、请求遥测 | 已定义于 `robot_arm.md`，未实现 |
| F4 | 遥测项 | CPU 使用率、内存占用、CPU 温度、网络延迟 | 未实现 |

### 2.2 性能层（P）

| # | 指标 | 定义（从哪到哪） | 目标值 | 测量方法 | 状态 |
|---|---|---|---|---|---|
| P1 | 玻璃到玻璃延迟 | 机器人端 DQBUF 时间戳 → 控制端上屏时间戳（同一帧） | 有线 <80ms；WiFi <150ms | 两端时钟对齐（NTP），帧头打时间戳 | 【需补齐接收/显示】 |
| P2 | 控制往返延迟 | 控制端发指令（带时间戳）→ 收到 ACK | <50ms | 指令带发送时间戳，ACK 回带 | 【需补齐控制通道】 |
| P3 | 帧率稳定性 | 连续帧出帧间隔 vs 目标 33ms | 抖动 <±5% | DQBUF 时间戳间隔统计 | 【当前可测】 |
| P4 | 分片丢包率 | 发送 frame_id 数 vs 接收收齐帧数 | 有线 <0.1%；WiFi <1% | 按 frame_id 连续性统计 | 【当前可测】 |

> P1 推导：精细操作时眼睛和手不能错位。200ms 已被人眼明显感知到手眼错位，故不支持 200。有线直连能提供低延迟低抖动的干净基线，故定 <80ms；WiFi 抖动大需缓冲余量，放宽到 <150ms。
> P4 推导：分片协议无 FEC，丢一片 = 丢一整帧（末片一丢整帧报废），故按帧统计丢包，而非按片。

### 2.3 可靠性层（R）

| # | 指标 | 目标值 | 判据 | 状态 |
|---|---|---|---|---|
| R1 | 指令可靠交付 | 5% 丢包下送达率 100% | 应用层 ACK + 超时重传 + 序号去重 | 【需补齐控制通道】 |
| R2 | 心跳 / 看门狗 | 心跳丢失 500ms 内机器人端自动停止 | 安全停止被触发 | 【需补齐】 |
| R3 | 断线重连 | <2s | 拔线 → 插回，恢复出帧时间 | 【需补齐】 |
| R4 | 长时无内存泄漏 | 72h RSS 稳定 | valgrind / RSS 曲线无持续上涨 | 【当前可测，硬考点】 |

> R4 重点：`frame.hpp` 的 `FrameQueue::push` 在队列满时 `delete[] q_.front().data` 丢最旧帧，主线程再 `delete[] f.data`——这套手动 new/delete 是泄漏高发区，也是「跑三天就崩」的经典死法。必须立成硬指标逼着用 valgrind 验证。
> R1 分层说明：TCP 只保证字节送到，不保证指令被执行；应用层 ACK 确认的是「指令被执行」，超时重传应对「应用卡死/崩溃」。这是「传输层可靠」与「应用层确认」两层的区别。

### 2.4 资源层（M）

| # | 指标 | 目标值 | 测量 | 状态 |
|---|---|---|---|---|
| M1 | 机器人端 CPU 占用 | <30% | top（采集 + 分片 + sendto 线程） | 【当前可测】 |
| M2 | 内存峰值 | 有界，不随运行时长增长 | RSS | 【当前可测】 |
| M3 | 视频码率 | ≈7Mbps（640×480@30 MJPEG 实测） | 字节数 × 8 / 秒 | 【当前可测】 |
| M4 | 功耗 | 记录即可 | 可选，不强求 | — |

> M3 推导：640×480@30 MJPEG 单帧约 30KB → ≈7Mbps。有线百兆、WiFi 均足够，此条验证「拿带宽换省 CPU」的可行性。

### 2.5 工程层（E）

| # | 指标 | 判据 |
|---|---|---|
| E1 | 错误路径处理 | 每个 ioctl / socket 返回值的失败分支都被检查并处理（当前部分已覆盖，需补全） |
| E2 | 接收端重组测试 | 覆盖乱序、重复片、丢片、魔数错 4 类用例 |
| E3 | 跨编译 | 两套工具链（ARM Cortex-A7 / RISC-V C906）各产出可运行产物 |
| E4 | 分级日志 | 能定位「哪一帧丢在哪」 |

## 3. 里程碑切分

按「当前可测 / 需补齐模块」划分验收范围，形成路线图：

### 里程碑 M1 —— 视频单向链路（当前代码可支撑）

只验收「当前可测」的 8 条：**P3、P4、R4、M1、M2、M3** + 部分的 **E1、E3**。

- 测量对象：`src/` 现有实现（`v4l2app` 采集 + `udpapp` 分片发送 + `frame` 队列）。
- 验收动作：加时间戳埋点 / frame_id 统计 / RSS 曲线 / valgrind，跑出真实数字对标。

### 里程碑 M2 —— 控制 + 遥测 + 接收显示（补齐模块后）

验收剩余 12 条：**P1、P2、R1、R2、R3** + F3、F4 + 完整 E2、E4。

- 需先补齐：TCP 控制通道（自定义二进制协议 + 应用层 ACK）、遥测上报、接收端解码 + 上屏显示。
- 补齐后 P1 才能测（需要接收端上屏的时间戳端点）、R1/R2/R3 才能测（需要控制通道）。

## 5. 验收即校准

目标值是「规格」不是「事实」。M1 跑完若 P3/P4/M1 任一不达标，按优先级校准：

1. 调架构（如 WiFi 阶段丢包超标 → 加 FEC 或降码率，而非无脑重传——视频丢一帧可容忍）
2. 调目标值（如 SG2002 的 CPU 撑不住 <30%，则回到场景重估，而非硬凑数字）
